# 功能完整性

用户的期望：**不要让他一个一个去发现问题。** 用户提的需求只是入口，交付物是"一个真实用户从头用到尾都顺"的功能。用户指出的问题，同类的都应该在他发现之前被处理掉。

只做字面需求是不够的。例如"加个停止按钮"，背后至少包含：停止后能不能继续、停止后的数据怎么展示、停止中途的那道题怎么处理、按钮放在列表还是详情、要不要确认、和删除的区别。这些都要在动手前想清楚。[examples.md](examples.md) 记录了这个项目里真实发生过的一次"用户提一个、修一个"，第一次用本技能时先读它。

## 工作流程

按顺序做，每一步都有产出，不要跳步。

### 1. 盘点：先弄清楚模块现在是什么样

- 读完整条链路：`backend/app/modules/<模块>/`（api → service → repository → models → schemas）和前端页面 `frontend/src/pages/<页面>.tsx`、`api/hooks.ts` 里的调用。
- 列出模块里的**对象**（如：评测运行、题目、结果）和每个对象的**状态**（如：排队中/运行中/已完成/已停止/已中断）。
- 列出能操作它的**角色**（admin / leader / member，见 [askdata.md](askdata.md)）和每个角色能看到、能做什么。
- **在真实应用里亲自用一遍**（登录对应账号，点一遍现有流程），截图记下现状。只看代码会漏掉对齐、文案、空状态这类问题。

### 2. 推演：把每个对象的生命周期走一遍

对每个对象画出状态机：怎么产生 → 中间有哪些状态 → 怎么结束 → 结束后还能做什么。对**每个状态**和**每个操作**都问：

- 这个状态下用户能做什么？需要的操作入口都在吗？（例：停止的评测要能继续、能删、能重跑）
- 这个操作之后呢？用户下一步自然想做什么？有没有一键直达？（例：看完失败题 → 想只重跑失败的题）
- 能撤销吗？不能撤销就要确认；能撤销就**不要**确认（确认会拖慢操作）。
- 做到一半中断了怎么办？（服务重启、网络断、用户关页面、并发操作）
- 这个状态下显示的数字和文字是真实的吗？会不会误导？（例：只跑了 38/100 题却显示"题数 100、通过率 71%"）
- 同一个操作在其他入口（列表、详情、另一个 tab）也能做吗？行为一致吗？

### 3. 找缺口：逐项过检查清单

打开 [checklist.md](checklist.md)，**逐节逐条**对照当前模块，把每个不满足的点写进缺口清单。不要凭印象跳过某一节；"这节应该没问题"恰恰是漏掉问题的地方。

每个缺口标优先级：

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 坏了、数据错、误导用户、会卡死 | 必须修 |
| P1 | 正常使用中会撞上的缺失（缺操作入口、缺状态、缺反馈、没对齐） | 直接做，不用问 |
| P2 | 锦上添花（快捷操作、估算、批量） | 成本低就顺手做，否则写进报告 |
| 决策 | 有多种合理做法、涉及产品取舍或不可逆 | 写进报告问用户，不擅自决定 |

只有"决策"类才需要问用户。P0/P1 是专业判断，直接做；把它们拿去问用户，等于又让用户自己去发现。

### 4. 实现：端到端一次做完

一个缺口的"做完"包括全部相关层，缺一层就是没做完：

- 后端：schema、service、api、权限检查、审计；数据库变化要有 migration（并同步测试夹具）。
- 接口类型：重新生成 `backend/openapi.json` 和 `frontend/src/api/schema.d.ts`。
- 前端：所有入口、所有状态的展示、错误提示、加载态；遵守 `chatbi-design-system` 技能（先读它）。
- 测试：后端为新的状态转换、并发/中断、权限写测试；前端纯函数写单测。
- 部署：后端代码打包在镜像里，改了必须重建容器（见 [askdata.md](askdata.md)），否则浏览器里看到的是旧行为。

### 5. 验证：在浏览器里逐角色、逐状态看

用 Playwright 登录（账号见 [askdata.md](askdata.md)），对**每个相关角色**、**每个状态**截图并亲眼检查：

- 空状态、加载中、进行中、部分完成、失败、成功、数据很多（滚动/换行/横向溢出）。
- 对齐：表头和单元格、按钮组、徽标、数字列右对齐；按钮文字和表头是否在一条线上。
- 没权限的角色看不到不该有的入口（是不渲染，不是置灰）。
- 真实地点一遍主流程（不是只调 API）：开始 → 中途操作 → 结束 → 后续操作。
- 验证中创建的测试数据，结束时清理掉，并告诉用户。

截图里发现的问题当场修、重新截图，直到满意再交付。

### 6. 交付：报告做了什么、验证了什么、留了什么

结尾报告用这个结构（简洁，不要罗列代码细节）：

1. **用户提的**：逐条说明怎么解决的。
2. **我自己发现并补上的**：按用户能感知的效果描述（"停止后可以继续"），不是按代码描述。
3. **验证情况**：在浏览器里走过哪些流程、哪些角色；测试结果。如实说明没验证到的部分。
4. **需要你决定的**：只列真正的"决策"类问题，每个给出推荐选项和理由。
5. **没做的 P2**：一句话列出，说明原因。

## 心态

- 用户提一个点，就把它当成一类问题的样本，找出同类的全部问题。
- 宁可多想一步。"用户大概不会这么用"通常是错的。
- 数据展示必须真实；部分完成、过期、估算的数字都要标明。
- 做完之前，自己先当一遍挑剔的用户。
